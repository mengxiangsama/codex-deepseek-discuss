# GPT + DeepSeek 项目协作

让当前 Codex / GPT 负责项目取证、提出自己的观点并与 DeepSeek 交叉讨论，通过 `ask_deepseek` 传递双方实际观点和证据。Skill 约束协作流程；MCP 工具负责连接 DeepSeek。Skill 本身不安装工具、不改变模型提供商配置。

## 确认任务和工具

- 先确定用户要分析、审查、设计还是实现。“先看、先讨论、先不要修改”表示只读；“实现、修复、改掉、按方案做”表示允许相应范围的代码变更。继承当前任务已有的授权，用户的新限制优先，不为已经授权的实现再次索要确认。
- 仅分析或审查时不改业务代码、不部署、不提交或发布。调用本 Skill 不是这些动作的额外授权。
- 用户说“只要 GPT、不用 DeepSeek”时遵从，不调用第二模型。
- 用户说“协作、一起分析、讨论、双方认可”时采用下文完整讨论流程，不能只调用一次独立审查就结束。用户明确仅要“第二意见/独立审查”时，可以在核对意见后直接综合；不得将此过程称为双方讨论或共识。
- 从实际可用工具中查找 `ask_deepseek`；名称可能带服务前缀，例如 `mcp__deepseek_discuss__ask_deepseek`。以当前工具声明为准，不硬编码某个宿主的调用方式或旧的 backend 参数。
- 工具缺失时明确报告“DeepSeek 未参与：工具不可用”，给出 GPT 自己的分析；必要时指出需接入 deepseek-discuss MCP。不要擅自修改全局配置，也不要用模拟回答代替调用。

## 代码开发时的模型选择

- 用户未指定模型时，代码开发、修复、重构和代码审查优先显式请求 `model="deepseek-flash"`；这是本 Skill 的默认偏好，用户明确指定其他模型时遵从。不要仅凭 Pro 名称推断编程能力更强。
- 截至 2026-10-26，官方 API 文档将 `deepseek-flash` 映射到 DeepSeek-V4.1-Flash-1017。选型依据是官方模型卡的编程/软件工程基准及更新说明，不代表已在用户的 Java 项目上完成 A/B 实测；版本映射会变化。用户再次询问最新模型或要求升级时重新核对官方文档。
- 依据：[API 模型映射](https://api-docs.deepseek.com/quick_start/pricing/)、[V4.1-Flash 官方比较表](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash)、[1017 更新模型卡](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash-1017)。不同基准版本、推理强度和 agent 框架的分数不能直接混比。
- 若当前工具声明支持 `backend` 且需要通过 API 精确选择模型，使用 `backend="api"`；新版 API-only 工具没有此参数时省略。不要假定旧 Harness 接入会采用 `model` 参数。
- 用调用结果中的 `requested_model` 和 `response_model` 核对请求与服务端标识。响应仅含别名时，不把它说成服务端证明了具体权重版本；只有文本回答时，说明缺少可验证元数据。
- 模型别名不可用或调用失败时如实报告，不静默切换模型或提高推理预算；保留用户的显式配置，不擅自提高输出上限或推理强度。

## 先取证，再给独立审查上下文

先阅读项目适用的 AGENTS.md 和与问题有关的真实代码、测试、调用链、配置结构。记录关键路径或行号，区分代码事实、业务假设和未知信息；没有项目代码或无法访问时明确限制，不能声称已读。

向 DeepSeek 提供自包含的最小上下文包，通常包括：

- 用户目标、任务边界、已确定的业务规则和待核实项；
- 相关代码片段、接口约定、简化调用链或脱敏错误；
- 希望其独立检查的问题，如状态迁移、并发、幂等、事务和测试缺口。

GPT 先基于代码形成自己的具体方案和理由，首轮给 DeepSeek 的上下文先保留事实与问题，让其独立判断。随后必须提供 GPT 的具体方案用于交叉审查，减少首轮相互迎合。代码量大时先缩小问题，不自动上传整个仓库或完整聊天。

DeepSeek 只看到工具参数中显式发送的内容，不能自行读取当前仓库。可用片段带仓库相对路径及必要行号，保留理解逻辑需要的结构。

发送前检查并剔除 API Key、密码、Cookie、令牌、连接凭据、私钥、客户个人资料和无关聊天内容。用户授权审查项目不等于授权发送秘密。不要传环境变量全集、密钥配置文件或未脱敏的请求头。

## 必须完成的讨论流程

1. **分别提出观点**：GPT 记录自己的具体选择、理由、假设与风险；调用实际工具取得 DeepSeek 的独立方案。检查调用成功后再引用其观点。失败时如实报告，不把错误包装成模型意见，不静默切换模型。
2. **交换具体方案**：独立审查后必须再次调用 DeepSeek。将 GPT 的具体选择与理由、DeepSeek 原观点、双方逐项分歧一起发送，要求逐项回答“同意 / 不同意 / 需修改”，并说明证据与反例。关键争议原句应准确引用；上下文可以精简，但不能删去影响判断的条件或把 GPT 推测写成 DeepSeek 原话。不能只问“你怎么看”或要求它附和 GPT。
3. **GPT 实质回应**：逐项核对 DeepSeek 的回应与代码事实。对反对意见明确选择接受、反驳或补证；必要时补读代码、运行授权范围内的诊断或测试。DeepSeek 的输出不能替代真实证据。若其误读用户需求或代码，明确纠正并将证据传回。
4. **不认可就继续分析**：任一方对影响最终方案的点仍不认可，针对该点提供新证据、具体反例或修订方案，继续调用 DeepSeek 讨论。不要固定“一轮追问即可”，不要在存在重要反对意见时声称达成共识。每轮应有证据或方案进展，不能仅为取得“同意”而重复无变化的付费调用。
5. **确认最终版本**：将收敛后的方案及关键修订发给 DeepSeek 明确确认，GPT 也独立核对。若上一轮已完整包含最终版本，且 DeepSeek 对所有关键项明确认可、GPT 接受其回应，可以直接结束；否则必须补发最终版本确认。DeepSeek 只提出修改建议时，不等于已认可 GPT 后续自行改写的版本。
6. **如实收口**：只有双方对同一最终版本的关键项均认可，才称为“双方共识”。业务规则缺失时向用户提出聚焦问题；证据不足、工具失败、预算限制或讨论停滞时，保留分歧并说明原因，不能伪造共识或无限空转。继续完成不依赖该缺口的分析。

讨论交付应让用户看清：GPT 的观点、DeepSeek 的观点、关键分歧与双方回应、最终共同认可的方案，以及仍未解决的事项。可用简短表格或准确短引文，不必重复两份完整长文。重要争议不能只给 GPT 单方面综合而隐藏 DeepSeek 的反对理由。

每次调用都提供自包含的必要上下文，不假定 DeepSeek 自动记得上次工具调用或能看到本聊天。进度更新明确区分“独立审查已完成”“正在交叉讨论”“最终版本已确认”。

工具请求成功才能说“DeepSeek 的观点”。不要把 GPT 的推测、预期答案、失败信息包装成 DeepSeek 已发言。模型身份只引用工具提供的请求/响应元数据；缺失时说未知，不能靠模型自报确定版本。

## 实现与交付

- 未有实现授权：交付证据、综合方案和仍待确认的业务问题。
- 已有实现授权：按综合方案实施，保留用户无关改动，运行与风险相称的验证。无需等待用户重复说一次“实现”。
- 对影响架构或资金等关键规则的实质偏离，先解释依据；需要用户业务选择时再澄清。
- 区分代码检查、自动测试、真实接口验证和部署结果，不把其中之一当成其他层面的成功。
- 按讨论流程区分观点来源并报告最终版本的确认状态。DeepSeek 从未成功返回时写“DeepSeek 未参与：原因”；仅后续讨论调用失败时写“独立审查已完成，交叉讨论/最终确认未完成”，保留已有观点与分歧。报告最终选择及验证结果。

## 调用示例

```text
用 $gpt-deepseek-collab 检查订单的支付回调和超时关闭，
先读代码，让 DeepSeek 独立审查，讨论后给出方案，暂不修改。
```

```text
用 $gpt-deepseek-collab 修复刚才确认的重复扣库存问题，
按已经确定的业务规则实现，并运行相关测试。
```
