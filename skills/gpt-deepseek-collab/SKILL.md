# GPT + DeepSeek 项目协作

让当前 Codex / GPT 负责项目取证与综合，通过 `ask_deepseek` 获取独立第二意见。Skill 约束协作流程；MCP 工具负责连接 DeepSeek。Skill 本身不安装工具、不改变模型提供商配置。

## 确认任务和工具

- 先确定用户要分析、审查、设计还是实现。“先看、先讨论、先不要修改”表示只读；“实现、修复、改掉、按方案做”表示允许相应范围的代码变更。继承当前任务已有的授权，用户的新限制优先，不为已经授权的实现再次索要确认。
- 仅分析或审查时不改业务代码、不部署、不提交或发布。调用本 Skill 不是这些动作的额外授权。
- 用户说“只要 GPT、不用 DeepSeek”时遵从，不调用第二模型。
- 从实际可用工具中查找 `ask_deepseek`；名称可能带服务前缀，例如 `mcp__deepseek_discuss__ask_deepseek`。以当前工具声明为准，不硬编码某个宿主的调用方式或旧的 backend 参数。
- 工具缺失时明确报告“DeepSeek 未参与：工具不可用”，给出 GPT 自己的分析；必要时指出需接入 deepseek-discuss MCP。不要擅自修改全局配置，也不要用模拟回答代替调用。

## 先取证，再给独立审查上下文

先阅读项目适用的 AGENTS.md 和与问题有关的真实代码、测试、调用链、配置结构。记录关键路径或行号，区分代码事实、业务假设和未知信息；没有项目代码或无法访问时明确限制，不能声称已读。

向 DeepSeek 提供自包含的最小上下文包，通常包括：

- 用户目标、任务边界、已确定的业务规则和待核实项；
- 相关代码片段、接口约定、简化调用链或脱敏错误；
- 希望其独立检查的问题，如状态迁移、并发、幂等、事务和测试缺口。

先请其基于证据独立判断，再提供 GPT 的完整方案用于交叉审查，减少首轮相互迎合。代码量大时先缩小问题，不自动上传整个仓库或完整聊天。

DeepSeek 只看到工具参数中显式发送的内容，不能自行读取当前仓库。可用片段带仓库相对路径及必要行号，保留理解逻辑需要的结构。

发送前检查并剔除 API Key、密码、Cookie、令牌、连接凭据、私钥、客户个人资料和无关聊天内容。用户授权审查项目不等于授权发送秘密。不要传环境变量全集、密钥配置文件或未脱敏的请求头。

## 调用、交叉质疑和综合

1. 调用实际工具获取独立意见。首轮重点要求其指出假设、风险与证据，不要求其代表 GPT 发言。
2. 检查调用是否成功，分清工具错误和模型回答。失败时如实概括错误并隐去秘密；仅在有合理依据时有限重试，不反复进行无变化的付费调用。
3. GPT 逐项核对其意见和仓库事实；对关键质疑补读代码或测试。DeepSeek 的输出是外部意见，不能替代代码证据、实时文档或用户授权。
4. 对影响结论的分歧，发送最小必要证据和具体反例进行定向追问。通常一轮追问即可；若仍有重要未决项，明确列出证据缺口、各方案取舍及 GPT 的判断。不要为了形式上的共识无限循环，也不要把日常技术取舍一律交回用户。
5. 若分歧涉及缺失的业务规则且会实质改变方案，向用户提出聚焦的问题；不依赖该答案的分析可以继续。

工具请求成功才能说“DeepSeek 的观点”。不要把 GPT 的推测、预期答案、失败信息包装成 DeepSeek 已发言。模型身份只引用工具提供的请求/响应元数据；缺失时说未知，不能靠模型自报确定版本。

## 实现与交付

- 未有实现授权：交付证据、综合方案和仍待确认的业务问题。
- 已有实现授权：按综合方案实施，保留用户无关改动，运行与风险相称的验证。无需等待用户重复说一次“实现”。
- 对影响架构或资金等关键规则的实质偏离，先解释依据；需要用户业务选择时再澄清。
- 区分代码检查、自动测试、真实接口验证和部署结果，不把其中之一当成其他层面的成功。
- 按需用“DeepSeek 的观点”和“GPT 的回应 / 综合”区分来源；调用失败时明确写“DeepSeek 未参与：原因”，然后给出 GPT 的独立结果。报告重要分歧、最终选择及验证结果，避免重复两份相同长文。

## 调用示例

```text
用 $gpt-deepseek-collab 检查订单的支付回调和超时关闭，
先读代码，让 DeepSeek 独立审查，讨论后给出方案，暂不修改。
```

```text
用 $gpt-deepseek-collab 修复刚才确认的重复扣库存问题，
按已经确定的业务规则实现，并运行相关测试。
```
